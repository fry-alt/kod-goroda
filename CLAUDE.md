# Правила работы — финал «Код города», МГТС, 26.11

Этот файл читают люди и ИИ-агенты (Claude Code, Codex, Cursor). Сначала он, потом код.

## Задача в одном абзаце
Работающий прототип ИИ-системы для HR стажёрской программы МГТС (6 месяцев, 6 ежемесячных опросов).
Два источника: **пульс-опрос стажёра** и **анкета наставника** (оценки 1–5 + открытые вопросы). Система
**сама получает новые ответы из внешнего сервиса анкет** (вебхук/API), привязывает их к стажёру и контрольному
периоду, добавляет к истории, пересчитывает анализ и **обновляет дашборд**. Дашборд: общая картина (кто заполнил
опрос, кто нет; «светофор» по стажёрам) → карточка стажёра (динамика его оценок и оценок наставника по 6 точкам,
расхождения, анализ комментариев ИИ, сигналы **с данными-основаниями**, краткое резюме и что делать HR).

Полный текст: [docs/case_full.md](docs/case_full.md) · анкеты и шкалы: [docs/surveys_structure.md](docs/surveys_structure.md) ·
данные: `data/case/Ответы стажеров.xlsx`, `data/case/Оценки наставников.xlsx` (5 стажёров СТ-001…005, 5 наставников
Н-001…005, «Месяц 1…6», 5 блоков: технический, коммерческий, административный, HR, IT).

## Демо на защите (это и есть критерий «готово»)
**Заполняем тестовую анкету в форме → ответ сам приходит в систему → привязан к СТ-00X и «Месяц N» →
история обновилась → анализ пересчитан → дашборд обновился без перезагрузки руками.**
Защита 4 мин + 2 мин вопросы, живого ноутбука может не быть → **скринкаст 30–40 сек** этого сценария в презентации.
Сдача до 13:25 в ЛК: презентация PDF/PPTX по брендбуку МГТС + слайд «Дополнительные материалы» (ссылки на репозиторий,
прототип, документацию). Брендбук: https://disk.yandex.ru/d/uXw7Qs1IOmeFAg

## API-контракт (бэк отдаёт, фронт рисует)
Все ответы JSON, русские названия показателей — как в xlsx.
- `GET /api/overview` →
  `{ "periods": [1..6], "current_period": 6,
     "survey_status": [ {"intern_id":"СТ-001","mentor_id":"Н-001","department":"Технический блок",
                         "periods": {"1": {"intern": true, "mentor": true}, ...}} ],
     "interns": [ {"intern_id","mentor_id","department","status":"green|yellow|red",
                   "intern_avg":4.3,"mentor_avg":4.5,"gap":0.2,"trend":-0.4,"signals":2,"reason":"коротко почему"} ],
     "kpi": {"responded_interns":"5/5","responded_mentors":"4/5","red":1,"yellow":2,"green":2},
     "version": 12 }`
- `GET /api/interns/{id}` →
  `{ "intern_id","mentor_id","department","status",
     "periods": [ {"period":1,"intern":{"Понятность задач":4, ...},"mentor":{"Понимание задач и ожиданий":4, ...},
                   "intern_avg":4.1,"mentor_avg":4.0,"gap":-0.1,
                   "comments":{"intern":{"Сложности за период":"…","Что мешает работать и развиваться":"…"},
                               "mentor":{"Комментарий о работе за период":"…","Сложности / ситуации для внимания":"…"}},
                   "comment_analysis":{"topics":["нагрузка"],"tone":"негатив","risk":true}} ],
     "pairs": [ {"intern":"Понятность задач","mentor":"Понимание задач и ожиданий","by_period":[[4,4],...]} ],
     "signals": [ {"id","level":"red|yellow","title","why",
                   "evidence":[{"source":"стажёр|наставник","period":4,"field":"Комфортность нагрузки","value":2,"quote":"…"}]} ],
     "summary":"2–3 предложения для HR","actions":["…","…"] }`
- `GET /api/version` → `{"version": 12, "last_event": {"intern_id":"СТ-003","period":7,"source":"стажёр","at":"12:01"}}`
  — фронт опрашивает раз в 3 с и перерисовывает, если версия выросла (так видно «дашборд обновился сам»).
- `POST /api/webhook/{form}` (`form` = `intern` | `mentor`) — приём ответа из сервиса анкет.
- `POST /api/import` — загрузка исторических xlsx (multipart, можно оба файла сразу).

## Логика «светофора» и сигналов (стартовая, Савелий уточняет)
- Пары показателей стажёр ↔ наставник для расхождений: «Понятность задач» ↔ «Понимание задач и ожиданий»;
  «Взаимодействие с командой» ↔ «Взаимодействие с наставником и командой»; «Интерес к задачам» ↔ «Вовлеченность и
  инициативность»; «Поддержка и обратная связь наставника» ↔ «Взаимодействие с наставником и командой» (условно).
- **Красный**: средняя < 3, или падение ≥ 1 балла к своей норме по 2+ показателям, или риск в комментарии, или пропуск опроса.
  **Жёлтый**: 3–3,9, расхождение стажёр/наставник ≥ 1,5, повторяющаяся жалоба в комментариях 2+ месяца. Иначе **зелёный**.
- Каждый сигнал обязан содержать `evidence` — конкретные оценки и цитаты, из которых он получен.
- Сравниваем человека с его собственной нормой (у всех своя «валюта» оценок), сигнал — если держится 2 из 3 периодов
  или подтверждён комментарием. Наработки: репозиторий Takeshhii/kod-goroda-ai, `app/signals.py` (личная норма, разрыв
  пары, пропуск опроса, риск в комментарии) — можно переносить.

## Как работаем в git (3 часа, 3 человека)
- Один репозиторий, ветка `main`. Перед началом работы и перед каждым push: `git pull --rebase`.
- **Маленькие коммиты каждые 20–30 минут**, сообщение по-русски: что сделано. Пуш сразу — не копить «на конец».
- Не трогаем чужие папки, не делаем `push --force`, не коммитим `.env` и ключи.
- Конфликт → не удалять чужой код, решить вдвоём в чате за 2 минуты.
- 12:50 — **заморозка**: `git tag final && git push --tags`. После этого только правки текста презентации.

## Правила для ИИ-агентов
- Сначала прочитать этот файл и `docs/case_full.md`. Если что-то расходится — прав кейс.
- Менять только папки своего владельца (см. таблицу). Контракт API менять только вместе с владельцем бэка и фронта.
- Без ключей LLM всё должно работать (офлайн-правила) — демо не может зависеть от сети.
- Не выдумывать цифры МГТС. Решение о человеке принимает HR; система даёт сигнал и основания.
- После изменений: `pytest` и ручная проверка сценария демо. Сломанное демо хуже недоделанной функции.
